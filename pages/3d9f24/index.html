# 一文讲透敏捷思想、敏捷宣言与12项原则

敏捷不是“没有计划”，也不是“需求可以随便改”，更不等于 Scrum。
敏捷是一套面向复杂环境和不确定需求的价值观、思维方式与管理原则。

# 摘要

传统预测型项目强调在前期尽可能明确范围、制定完整计划，并按计划完成交付。这种方式适合需求稳定、技术成熟、变化较少的场景。

但在软件研发、数字化产品、创新业务和复杂系统建设中，项目团队往往无法在项目开始时准确预测全部需求。客户对最终产品的认识会逐步加深，市场、技术和组织环境也可能持续变化。

敏捷的核心不是取消管理，而是改变管理方式：

以客户价值为中心，通过自组织团队、小步交付、快速反馈和持续改进，主动应对复杂性与变化。

本文将从以下六个方面建立完整知识体系：

  1. 为什么需要敏捷；
  2. 敏捷思想的底层逻辑；
  3. 敏捷宣言的四项价值观；
  4. 敏捷的12项原则；
  5. 敏捷的常见误区；
  6. PMP考试中的敏捷答题逻辑。

# 一、为什么需要敏捷

# 1. 预测型方法的基本假设

预测型生命周期通常采用以下逻辑：

收集和确认完整需求
        ↓
制定详细范围、进度和成本计划
        ↓
按照计划执行
        ↓
测试、验收并统一交付

这种方式隐含一个重要假设：

项目团队能够在前期较准确地理解需求、预测工作并确定解决方案。

因此，预测型方法更适合：

  • 需求相对明确和稳定；
  • 技术路线成熟；
  • 可交付成果容易定义；
  • 工作可以提前充分分解；
  • 变更概率和不确定性较低；
  • 合规、工程或合同边界较强的项目。

# 2. 复杂项目中的现实问题

在复杂项目中，项目初期通常存在大量未知因素：

  • 客户只能描述问题，无法准确描述最终产品；
  • 用户看到实际成果后才知道自己真正需要什么；
  • 市场环境和竞争策略持续变化；
  • 新技术的可行性需要通过实验验证；
  • 不同干系人对最终成果存在不同理解；
  • 项目周期越长，初始计划失效的概率越高。

如果团队仍然坚持“先把全部需求确定，再进行一次性交付”，可能出现一种典型结果：

项目按原计划完成了，但交付的产品已经不能解决客户当前的问题。

敏捷正是为了解决这种“高变化、高不确定性、需要持续学习”的问题而产生。

# 1. 价值优先：先做最值得做的事情

传统项目容易把“是否按计划完成任务”作为主要评价标准。

敏捷更关注：

  • 当前最能解决客户问题的工作是什么；
  • 哪项功能能够最快产生业务价值；
  • 哪项假设最需要尽早验证；
  • 哪项风险如果不提前处理，后续代价最高；
  • 哪些功能即使不做，也不会影响核心目标。

因此，敏捷团队通常优先安排：

  1. 业务价值最高的工作；
  2. 风险最大的工作；
  3. 不确定性最高的工作；
  4. 最需要反馈验证的工作；
  5. 能够形成最小可用增量的工作。

敏捷并不追求平均地推进所有工作，而是持续优化价值交付顺序。

# 2. 小步交付：把大型目标拆成可验证的增量

敏捷不会长期封闭开发，等全部功能完成后一次性交付，而是将大型产品拆分成多个较小的、可使用的增量。

以电商系统为例，可以逐步交付：

交付批次 可用增量
第1次 商品浏览和搜索
第2次 购物车
第3次 创建订单
第4次 在线支付
第5次 售后、评价和退款

每次交付都应尽量形成客户可以使用、测试或评价的成果，而不仅是完成一份设计文档、一个代码框架或若干中间任务。

小步交付可以：

  • 提前实现部分业务价值；
  • 缩短从想法到验证的时间；
  • 及早发现方向性错误；
  • 降低一次性交付失败的风险；
  • 减少大量返工；
  • 提高客户对项目进度的可见性。

# 3. 快速反馈：用真实结果代替长期猜测

敏捷认为，复杂问题很难仅依靠前期分析获得全部正确答案。

与其长时间讨论“客户可能需要什么”，不如尽快做出可见成果，让客户和用户基于真实产品提供反馈。

常见反馈来源包括：

  • 客户评审；
  • 产品演示；
  • 用户试用；
  • 自动化测试；
  • 运营和使用数据；
  • 技术实验；
  • 迭代评审；
  • 团队回顾。

反馈越早，修正错误所需的成本通常越低。

# 4. 持续适应：计划应根据新信息不断更新

敏捷不否定计划，而是否定“计划一旦制定就不能变化”。

敏捷计划具有以下特点：

  • 分层规划：愿景、路线图、发布、迭代和每日计划；
  • 滚动式规划：近期详细、远期概略；
  • 渐进明细：随着信息增加逐步细化；
  • 短周期调整：定期基于反馈更新优先级；
  • 价值驱动：计划服务于价值，而不是价值服从计划。

因此，敏捷中的计划是一个持续更新的决策工具，而不是不可修改的命令。

# 5. 团队自组织：从控制团队转向赋能团队

敏捷团队通常是跨职能团队，团队成员共同决定：

  • 如何完成目标；
  • 如何分解工作；
  • 如何分工与协作；
  • 如何解决技术问题；
  • 如何控制质量；
  • 如何改善团队工作方式。

敏捷领导者主要承担服务型领导职责：

  • 清除障碍；
  • 协调资源；
  • 促进沟通；
  • 保护团队；
  • 提供环境和支持；
  • 促进团队自主决策；
  • 帮助团队持续成长。

自组织并不等于没有目标、规则和责任，而是：

管理者明确目标、价值、边界和约束，团队自主决定实现方式。

# 6. 持续改进：经验教训立即转化为行动

传统项目可能只在收尾阶段总结经验教训。

敏捷团队会在每个短周期后反思：

  • 哪些事情做得好；
  • 哪些事情没有达到预期；
  • 问题的根本原因是什么；
  • 哪些流程、工具或协作方式需要调整；
  • 下一迭代采取哪项具体改进行动。

经验教训不是为了归档，而是为了立即改善下一轮工作。

# 三、敏捷宣言的四项价值观

2001年，17位软件开发实践者共同提出《敏捷软件开发宣言》。敏捷宣言包含四组价值取向。

# 价值观一：个体和互动高于流程和工具

流程和工具具有价值，但最终完成项目的是人。

如果团队成员之间缺少直接沟通，即使拥有先进工具和完整流程，也可能出现：

  • 需求理解偏差；
  • 信息在传递过程中失真；
  • 问题长期得不到澄清；
  • 团队成员只完成局部任务，不关注整体价值；
  • 流程成为推卸责任的依据。

敏捷强调：

工具和流程应当服务于人与人的协作，而不能代替沟通、判断和责任。

# 正确理解

  • 需要合理流程，但避免流程主义；
  • 需要协作工具，但不能只依赖系统状态；
  • 复杂问题优先直接沟通；
  • 冲突应通过协作解决，而不是仅依赖流程升级。

# 常见误区

错误理解：

敏捷项目不需要流程和工具。

正确理解：

流程和工具仍有价值，但个体能力、有效互动和团队协作更加重要。

# 价值观二：可工作的产品高于详尽的文档

敏捷反对的不是文档，而是以文档代替真实交付。

真正能够证明项目取得进展的是：

  • 产品能够正常运行；
  • 功能通过测试；
  • 满足验收标准；
  • 用户能够实际使用；
  • 已形成潜在可发布的产品增量。

以下内容不能单独证明项目已经取得真实进展：

  • 已经编写大量需求文档；
  • 已完成技术设计；
  • 已经写了大量代码；
  • 任务状态显示完成80%；
  • 团队成员投入了很多时间。

敏捷中的文档应当是“刚刚足够”的：

  • 能支持开发和测试；
  • 能支持运营和维护；
  • 能满足审计与合规要求；
  • 能够被目标读者实际使用；
  • 维护成本与业务价值匹配。

# 常见误区

错误理解：

敏捷项目不写文档。

正确理解：

敏捷反对过度文档，优先确保产品可工作，同时保留必要、有效、可维护的文档。

# 价值观三：客户合作高于合同谈判

合同能够明确商业边界、责任和约束，但无法替代持续协作。

复杂项目中，客户需求可能随着产品认知、市场变化和用户反馈不断调整。如果团队只强调“合同中没有写”，很容易形成买卖双方对立。

敏捷更强调：

  • 客户持续参与；
  • 团队频繁展示成果；
  • 双方共同分析变化；
  • 通过调整优先级实现价值最大化；
  • 共同解决问题，而不是相互推卸责任。

# 常见误区

错误理解：

敏捷项目不需要合同。

正确理解：

合同仍然重要，但合同不能成为拒绝沟通和停止合作的工具。

# 价值观四：响应变化高于遵循计划

敏捷项目仍然需要计划，但计划必须能够响应新信息。

典型的敏捷计划层级包括：

产品愿景
   ↓
产品路线图
   ↓
发布计划
   ↓
迭代计划
   ↓
每日工作计划

越接近当前的工作，计划越详细；越远期的工作，计划越概略。

当客户反馈、市场环境、技术验证或风险发生变化时，团队应重新评估计划，而不是为了维护原计划而继续交付低价值成果。

# 常见误区

错误理解：

敏捷项目没有计划，团队想到什么就做什么。

正确理解：

敏捷不是不计划，而是持续计划、渐进明细和滚动调整。

# 四项价值观的记忆方法

四项价值观可以记为：

人、果、合作、应变。

关键词 对应价值观
人 个体和互动高于流程和工具
果 可工作的产品高于详尽的文档
合作 客户合作高于合同谈判
应变 响应变化高于遵循计划

进一步可记为：

重人不轻流程，重果不废文档，重合作不弃合同，重应变不无计划。

# 四、敏捷的12项原则

敏捷宣言说明“更重视什么”，12项原则进一步说明“应该怎样行动”。

# 原则1：尽早并持续交付价值

最重要的目标是通过尽早并持续交付有价值的产品，使客户满意。

关键词：

  • 尽早交付；
  • 持续交付；
  • 客户价值；
  • 客户满意。

敏捷不主张等所有功能全部完成后再让客户看到成果，而是尽快交付最有价值的可用增量。

在PMP场景题中，如果题目询问团队应优先处理什么，通常应优先考虑：

能够最快交付客户价值、验证假设或降低风险的工作。

# 原则2：欢迎有价值的需求变化

即使进入开发后期，敏捷也欢迎能够为客户创造竞争优势的变化。

但“欢迎变化”不等于：

  • 无条件接受所有需求；
  • 不评估成本、风险和价值；
  • 随意打断当前迭代；
  • 客户提出什么就立即开发；
  • 不管理范围和优先级。

更合理的处理过程是：

理解变更原因
    ↓
分析业务价值
    ↓
评估影响和风险
    ↓
加入产品待办事项
    ↓
重新排序优先级
    ↓
在适当迭代实施

对已经开始的迭代，一般应保护迭代目标，避免无序插入工作；紧急情况则需要团队和产品负责人共同评估。

# 原则3：频繁交付可工作的产品

敏捷强调以几周到几个月为周期频繁交付，并倾向采用更短周期。

短周期交付能够：

  • 缩短反馈时间；
  • 降低方向错误的风险；
  • 及时发现需求偏差；
  • 提前产生业务收益；
  • 提高项目透明度；
  • 降低大型集成风险。

需要特别注意：

“完成了设计”“完成了编码”或“完成了测试方案”不一定等于形成可工作的产品增量。

# 原则4：业务人员与开发人员持续合作

业务和交付团队需要在整个项目过程中保持高频、直接和持续的协作。

这样可以：

  • 减少需求层层传递造成的信息失真；
  • 及时澄清业务规则；
  • 快速做出取舍决策；
  • 缩短问题等待时间；
  • 建立对产品目标的一致理解。

该原则强调的是持续协作，而不是机械地要求所有成员每天参加固定会议。

# 原则5：围绕有动力的个体建设项目

敏捷强调为团队提供：

  • 明确的目标；
  • 必要的资源；
  • 合适的工作环境；
  • 决策授权；
  • 专业支持；
  • 充分信任。

敏捷领导者不应通过持续监控和微观管理解决问题，而应优先：

  • 清除障碍；
  • 促进团队讨论；
  • 提供辅导或培训；
  • 建立心理安全；
  • 鼓励团队自主解决问题。

# 原则6：直接、实时沟通最有效

面对面沟通是团队内部及团队之间传递信息最有效、最高效的方法。

在分布式团队中，视频会议、实时语音、屏幕共享和在线白板也属于高互动沟通。

面对面或实时沟通的优势包括：

  • 能立即提问；
  • 能立即澄清；
  • 可观察语气和反馈；
  • 减少往返等待；
  • 有利于处理复杂问题和冲突。

PMP题目中出现需求歧义、团队冲突或干系人误解时，通常应优先进行直接沟通，而不是立即上报或只发送书面通知。

# 原则7：可工作的产品是衡量进展的主要标准

敏捷用真实可用的产品衡量进展，而不是仅依据活动完成比例。

以下指标不能单独证明真正进展：

  • 已投入多少工时；
  • 已完成多少任务；
  • 已消耗多少预算；
  • 写了多少代码；
  • 文档完成了多少页；
  • 功能自称完成90%。

一个功能只有满足团队的完成定义，例如完成编码、测试、集成并达到验收标准，才可以被视为完成。

# 原则8：保持可持续的工作节奏

敏捷倡导发起人、开发人员和用户能够长期保持稳定节奏。

长期依赖加班和突击可能导致：

  • 缺陷率上升；
  • 团队疲劳；
  • 判断质量下降；
  • 技术债务增加；
  • 人员流失；
  • 实际交付速度持续下降。

敏捷关注长期稳定的交付能力，而不是短期通过透支团队获得表面速度。

# 原则9：持续关注技术卓越和良好设计

技术卓越和良好设计能够增强团队响应变化的能力。

常见实践包括：

  • 自动化测试；
  • 持续集成；
  • 持续交付；
  • 代码评审；
  • 重构；
  • 测试驱动开发；
  • 统一编码规范；
  • 缺陷预防；
  • 技术债务管理。

敏捷绝不意味着“先快速上线，质量以后再说”。

质量较差的系统会让后续每次修改越来越困难，最终失去敏捷性。

# 原则10：以简洁为本

简洁是最大限度减少不必要工作的艺术。

常见浪费包括：

  • 提前开发尚未确认的功能；
  • 编写无人使用的文档；
  • 设计远超当前需求的复杂架构；
  • 进行不产生价值的审批和汇报；
  • 同时启动过多工作；
  • 重复交接和等待；
  • 因质量问题造成返工。

简洁不等于粗糙，而是：

在满足质量、合规和价值目标的前提下，采用最简单有效的解决方案。

# 原则11：最佳成果来自自组织团队

最好的架构、需求和设计来自自组织团队。

管理者和产品负责人通常负责明确：

  • 为什么要做；
  • 要创造什么价值；
  • 优先级是什么；
  • 项目的约束和边界是什么。

团队负责决定：

  • 如何实现目标；
  • 如何拆分工作；
  • 如何分工协作；
  • 如何解决技术问题；
  • 如何改进过程。

自组织的基础是清晰目标、充分授权、透明信息和团队责任。

# 原则12：定期反思并调整

团队应定期反思如何提高效率，并相应调整行为。

Scrum中的典型实践是迭代回顾会议。

团队需要讨论：

  • 哪些做得好，应继续保持；
  • 哪些没有达到预期；
  • 问题的根本原因是什么；
  • 下一迭代准备采取哪项具体改进；
  • 如何验证改进是否有效。

回顾的目的不是追究个人责任，而是改进系统、流程、协作和团队能力。

# 五、12项原则的主题化记忆

孤立背诵12项原则容易混乱，可以按五个主题记忆。

# 1. 客户价值：原则1—4

  • 尽早持续交付价值；
  • 欢迎有价值的变化；
  • 频繁交付可工作的产品；
  • 业务与开发持续合作。

核心逻辑：

围绕客户价值，通过持续交付和反馈调整产品。

# 2. 团队与协作：原则5、6、11

  • 信任有动力的团队成员；
  • 采用直接、高效的沟通方式；
  • 依靠自组织团队创造最佳成果。

核心逻辑：

通过信任、授权和协作，让团队自主解决问题。

# 3. 产品与质量：原则7、9

  • 用可工作的产品衡量进展；
  • 通过技术卓越和良好设计内建质量。

核心逻辑：

以真实成果证明进度，以内建质量保持持续交付能力。

# 4. 节奏与简洁：原则8、10

  • 保持可持续工作节奏；
  • 最大限度减少不必要工作。

核心逻辑：

不透支团队，不做没有价值的工作。

# 5. 持续改进：原则12

  • 定期反思；
  • 采取改进行动；
  • 验证改进效果。

核心逻辑：

每一个迭代都比上一个迭代更好。

# 12项原则口诀

早交付、迎变化、频交付、常合作；
信团队、重沟通、看成果、可持续；
保质量、求简洁、自组织、常改进。

# 六、敏捷思想、宣言、原则与实践的关系

敏捷体系可以分为四个层次：

层次 回答的问题 示例
敏捷思想 为什么需要敏捷 通过反馈适应复杂性和不确定性
敏捷宣言 我们更重视什么 响应变化高于遵循计划
敏捷原则 应该按照什么原则行动 即使后期也欢迎有价值的变化
敏捷实践 实际工作中怎么做 产品待办列表、迭代评审、回顾会议

另一个例子：

层次 具体内容
敏捷思想 价值驱动
敏捷宣言 可工作的产品高于详尽文档
敏捷原则 可工作的产品是衡量进展的主要标准
敏捷实践 完成定义、产品增量、迭代演示、自动化测试

因此：

Scrum、看板、极限编程不是敏捷思想本身，而是落实敏捷思想的框架、方法或实践。

# 七、敏捷不是什么

# 1. 敏捷不等于没有计划

敏捷使用适应性计划、滚动式规划和渐进明细。

错误做法：

  • 团队没有目标；
  • 没有优先级；
  • 想到什么就做什么；
  • 不评估风险和资源；
  • 不管理发布节奏。

正确做法：

  • 用产品愿景明确方向；
  • 用路线图表达中长期目标；
  • 用发布计划协调价值交付；
  • 用迭代计划管理近期工作；
  • 根据反馈持续调整。

# 2. 敏捷不等于没有文档

敏捷保留：

  • 对开发有帮助的文档；
  • 对测试和维护有帮助的文档；
  • 满足法规、审计和合同要求的文档；
  • 能降低沟通和交接成本的文档。

敏捷删除的是无价值、无人使用、维护成本过高的文档。

# 3. 敏捷不等于随意变更

敏捷欢迎有价值的变化，但仍然需要：

  • 价值评估；
  • 影响分析；
  • 优先级排序；
  • 产品负责人决策；
  • 迭代边界管理；
  • 透明沟通。

# 4. 敏捷不等于只追求速度

敏捷追求的是：

更早、更持续、更可靠地交付价值。

敏捷同时强调：

  • 产品质量；
  • 客户满意；
  • 技术卓越；
  • 可持续节奏；
  • 团队健康；
  • 风险降低；
  • 持续学习。

# 5. 敏捷不等于 Scrum

两者关系如下：

敏捷：价值观、思想和原则
Scrum：实现敏捷的一种框架
1
2

除Scrum外，常见敏捷方法或实践还包括：

  • 看板；
  • 极限编程；
  • 精益产品开发；
  • 水晶方法；
  • 特性驱动开发；
  • Scrum与看板的混合实践。

# 八、预测型与敏捷型的关键差异

比较维度 预测型 敏捷型
需求 前期尽量完整确定 允许逐步发现和细化
计划 前期详细规划 分层、滚动、持续规划
交付 阶段末或项目末集中交付 短周期频繁交付
变更 尽量控制和减少 评估价值后主动适应
客户参与 里程碑或验收阶段参与 全过程持续合作
进度衡量 计划完成率、里程碑 可工作的产品增量
团队管理 项目经理安排和控制 自组织团队、服务型领导
风险处理 前期分析和计划控制 尽早验证、高频反馈
文档 相对详细和完整 刚刚足够、面向价值
适用场景 稳定、可预测 复杂、高变化、不确定

二者并不是绝对对立。在现实项目中，也可以采用混合型生命周期：

  • 总体采用预测型治理；
  • 研发工作采用迭代或敏捷方式；
  • 硬件采用预测型；
  • 软件采用增量或敏捷型；
  • 固定里程碑，迭代内灵活交付。

选择生命周期的根本依据不是流行程度，而是项目的：

  • 需求确定性；
  • 技术确定性；
  • 变更频率；
  • 交付紧迫度；
  • 合规程度；
  • 干系人参与能力；
  • 团队成熟度。

# 2. 常见正确选项倾向

敏捷题目中通常优先选择：

  • 与团队面对面讨论；
  • 促进团队自主解决问题；
  • 与产品负责人确认价值和优先级；
  • 邀请客户参与产品评审；
  • 将新需求加入产品待办事项；
  • 按价值、风险和依赖关系重新排序；
  • 通过回顾会议识别并实施改进；
  • 清除团队障碍；
  • 提供辅导、培训和支持；
  • 保护迭代目标；
  • 通过短周期交付验证假设；
  • 使用信息发射源提高透明度；
  • 与干系人共同寻找解决方案。

# 3. 常见错误选项倾向

应谨慎选择或通常排除：

  • 立即上报高级管理层；
  • 立即替换或处罚团队成员；
  • 项目经理单方面作出专业技术决定；
  • 拒绝所有变化；
  • 让客户直接给开发人员持续插入任务；
  • 要求团队长期加班赶进度；
  • 为满足计划而牺牲质量；
  • 只用任务完成百分比判断进度；
  • 用合同条款代替客户协作；
  • 绕过产品负责人直接改变优先级；
  • 未分析根因就修改流程或人员。

# 4. 四类高频场景

# 场景一：客户提出新需求

推荐思路：

  1. 理解需求和业务价值；
  2. 与产品负责人讨论；
  3. 加入产品待办事项；
  4. 评估影响；
  5. 重新排序；
  6. 在适当迭代中实施。

不应立即承诺，也不应直接拒绝。

# 场景二：团队成员发生冲突

推荐思路：

  1. 促进双方直接沟通；
  2. 理解冲突根因；
  3. 引导团队共同制定解决方案；
  4. 必要时提供辅导；
  5. 在回顾会议中改善协作机制。

不应首先处罚或上报。

# 场景三：迭代中出现阻碍

推荐思路：

  1. 确认阻碍对迭代目标的影响；
  2. 敏捷领导者负责促进和清除障碍；
  3. 与团队和相关方协调资源；
  4. 保持信息透明；
  5. 复盘阻碍产生原因。

# 场景四：产品质量下降

推荐思路：

  1. 不通过降低质量标准换取速度；
  2. 检查完成定义；
  3. 与团队分析根因；
  4. 优先偿还关键技术债务；
  5. 增加自动化测试、重构或质量实践；
  6. 调整工作量，恢复可持续节奏。

# 十、典型案例：数据分析平台如何采用敏捷

假设团队要建设一个企业级数据分析平台，初始需求包括：

  • 数据接入；
  • 指标管理；
  • 自助查询；
  • 可视化看板；
  • 权限管理；
  • 智能问数；
  • 数据质量；
  • 告警和订阅。

如果采用一次性交付，团队可能在一年后才交付完整平台。期间业务变化可能导致大量功能失效。

敏捷方式可以按价值和风险拆分：

# 第1个增量：验证核心价值

  • 接入一个核心数据源；
  • 建立少量关键指标；
  • 提供基础查询和一个业务看板；
  • 邀请真实用户试用。

目标不是功能完整，而是验证：

  • 指标口径是否正确；
  • 用户是否愿意使用；
  • 查询性能是否满足需求；
  • 最核心的业务价值是否成立。

# 第2个增量：扩大业务覆盖

  • 增加数据源；
  • 完善指标管理；
  • 增加权限控制；
  • 优化使用体验。

# 第3个增量：提高效率

  • 引入自助取数；
  • 增加订阅与告警；
  • 建立数据质量监控；
  • 提供使用分析。

# 第4个增量：探索智能化

  • 增加自然语言问数；
  • 引入语义层；
  • 建立SQL安全和权限校验；
  • 通过用户反馈逐步提升准确率。

在每个增量后，团队都应获取业务反馈，并重新判断：

  • 哪些功能价值最高；
  • 哪些需求不再需要；
  • 哪些风险需要提前解决；
  • 下一次应该交付什么。

这正是“价值优先—小步交付—快速反馈—持续适应”的完整闭环。

# 1. 敏捷核心思想

以客户价值为中心，通过自组织团队、小步交付、快速反馈和持续改进，主动适应变化。

# 2. 敏捷宣言

人、果、合作、应变。

  • 个体和互动高于流程和工具；
  • 可工作的产品高于详尽的文档；
  • 客户合作高于合同谈判；
  • 响应变化高于遵循计划。

信团队、重沟通、看成果、可持续；
保质量、求简洁、自组织、常改进。

# 4. 敏捷领导者关键词

  • 建立信任；
  • 保护团队；
  • 支持持续改进。

  • 先团队协作，后管理干预；
  • 先价值评估，后接受变化；
  • 先找根因，后制定措施；
  • 先保护质量和节奏，不靠长期加班；
  • 以可工作的产品衡量进展。

# 十二、总结

敏捷的本质不是速度，也不是取消流程，而是一种适应复杂性的管理方式。

它通过以下机制降低不确定性：

  1. 以客户价值决定工作优先级；
  2. 将大型目标拆成小型可用增量；
  3. 尽早向客户和用户展示真实成果；
  4. 根据反馈持续调整需求和计划；
  5. 依靠跨职能、自组织团队完成工作；
  6. 将质量内建到开发过程中；
  7. 通过定期回顾持续改进。

最终可以用一句话概括：

敏捷不是更快地执行一份固定计划，而是通过更快地学习，持续找到并交付真正有价值的成果。

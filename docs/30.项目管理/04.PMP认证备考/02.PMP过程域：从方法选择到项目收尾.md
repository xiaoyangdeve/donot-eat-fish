# PMP过程域：从方法选择、范围进度财务到项目收尾

过程域不是“十大知识领域的机械拼接”，而是一条完整的交付链：

> **选择合适方法 → 建立整合计划 → 定义范围 → 安排进度与资源 → 管理财务和质量 → 处理风险与采购 → 维护工件 → 交付价值 → 控制变更 → 验收收尾。**

![预测型与适应型主流程](/donot-eat-fish/img/project-management/pmp-exam/predictive-adaptive-main-flow.png)

## 第一记：确定适当的项目方法

### 1. 五种生命周期的本质区别

| 方法 | 需求确定时点 | 交付方式 | 适用场景 | 考试关键词 |
|---|---|---|---|---|
| 预测型 | 前期较明确 | 一次或少量阶段性交付 | 技术成熟、合规严格、变更代价高 | 基准、CCB、WBS、正式验收 |
| 迭代型 | 逐步细化 | 反复优化同一成果 | 原型、研发、技术不确定 | 反馈、渐进明细、反复试验 |
| 增量型 | 功能可分批确定 | 分批交付可用部分 | 快速上市、分阶段投产 | 每次增加功能、早期价值 |
| 敏捷/适应型 | 持续变化 | 短迭代、增量交付 | 市场变化快、客户高参与 | 待办列表、迭代、站会、评审 |
| 混合型 | 不同部分不同 | 预测+敏捷组合 | 硬件+软件、监管+创新、供应商固定 | 按组件/阶段裁剪 |

![生命周期选择决策树](/donot-eat-fish/img/project-management/pmp-exam/lifecycle-selection-decision-tree.png)

**考试判断：**“适应型=迭代+增量”是一种便于记忆的概括，但真正选择时还要看团队能力、客户参与度、治理约束、风险、合规和供应商模式。

### 2. 混合型不是“计划时预测、执行时敏捷”

混合型的核心是**按工作特征裁剪**。例如智能手机项目中，软件需求频繁变化，可采用敏捷；摄像头由拒绝渐进协作的供应商交付，则该组件采用预测型合同和里程碑管理。整体应描述为“以敏捷为主，包含预测组件”，而不是把整个计划阶段和执行阶段粗暴切开。

## 第三记：整合项目规划活动

项目管理计划是“如何管理项目”的总规则，它整合范围、进度、成本、质量、资源、沟通、风险、采购、干系人等子计划与基准。

### 基准与管理计划的区别

| 类型 | 本质 | 典型使用者 | 变更方式 |
|---|---|---|---|
| 范围/进度/成本基准 | 获批的绩效测量参照 | 团队、项目经理、治理层 | 正式变更控制 |
| 各知识领域管理计划 | 如何规划、执行、监控和变更 | 项目经理及相关责任人 | 按配置/变更规则更新 |

敏捷环境中，整合规划通过多层级计划完成：愿景与路线图、发布计划、迭代计划、每日同步。产品负责人说明价值和优先级，团队拆分任务、估算并自主分工。

## 第四记：规划和管理范围

### 1. 范围链路

1. 项目章程提供高层级需求和授权；
2. 收集需求并记录；
3. 定义项目和产品范围；
4. 创建WBS形成范围基准；
5. 控制质量得到“核实的可交付成果”；
6. 确认范围获得客户/发起人的正式验收。

![需求收集工具地图](/donot-eat-fish/img/project-management/pmp-exam/requirements-collection-tool-map.png)

### 2. 需求收集工具的场景化选择

| 场景 | 优选工具 | 原因 |
|---|---|---|
| 少数关键人员、内容敏感 | 访谈 | 深入、保密、可追问 |
| 多部门目标冲突，需要一致意见 | 引导式研讨会 | 跨职能同步、快速达成共识 |
| 大量分散用户、时间紧 | 问卷调查 | 覆盖广、周转快、便于统计 |
| 用户说不清需求 | 原型法、观察 | 通过实物/行为揭示隐性需求 |
| 创意不足 | 头脑风暴 | 广泛发散 |
| 大量创意需分类排序 | 亲和图、名义小组、投票 | 聚类与优先级决策 |
| 需要对比行业水平 | 标杆对照 | 识别差距和最佳实践 |

### 3. 高频范围术语

| 工件 | 关键内容 | 高频误区 |
|---|---|---|
| 项目范围说明书 | 产品范围描述、可交付成果、验收标准、除外责任 | 不是高层授权文件 |
| WBS | 以可交付成果为导向的分解，遵守100%规则 | 不是组织结构图，不直接表示责任人 |
| WBS词典 | 工作包详细描述、责任、假设、验收信息 | 与WBS配套使用 |
| 需求跟踪矩阵RTM | 需求来源、目标、设计、测试、验收的双向追踪 | 可避免遗漏测试和“做完却不满意” |
| 范围管理计划 | 如何定义、确认和控制范围 | 不包含具体产品功能 |

### 4. 验收失败如何判断

- 因缺陷被拒收：先看**控制质量、检查和测试**是否充分；
- 因需求遗漏被拒收：检查**需求跟踪矩阵、范围定义、持续评审**；
- 敏捷中避免验收失败：明确验收标准和DoD，频繁演示并获取反馈；
- 客户提出新功能：预测型先走变更流程；敏捷型进入产品待办列表，由产品负责人按价值重排。

## 第五记：规划和管理进度

![进度与估算工具](/donot-eat-fish/img/project-management/pmp-exam/schedule-estimation-tools.png)

### 1. 进度规划核心

- **分解**：把工作包细化为活动；
- **滚动式规划**：近期详细、远期粗略，适合长期或不确定项目；
- **网络分析/关键路径**：判断总工期、浮动时间和延期影响；
- **资源平衡**：解决严重资源冲突，可能延长关键路径；
- **资源平滑**：在浮动时间内调整，不改变关键路径；
- **假设情景分析/模拟**：评估不确定性和多种条件；
- **赶工**：增加成本/资源换时间；
- **快速跟进**：并行原本顺序工作，增加返工和风险。

### 2. 预测型估算方法

| 方法 | 适用场景 | 精度/成本 |
|---|---|---|
| 类比估算 | 早期信息少，有相似项目历史 | 快、成本低、精度较低 |
| 参数估算 | 数量与成本/工时存在可靠统计关系 | 数据可靠时精度高 |
| 三点估算 | 高风险、高不确定活动 | 考虑乐观/最可能/悲观 |
| 自下而上 | 可细化到活动/工作包 | 精度高、耗时高 |
| 专家判断 | 缺乏数据但有专业经验 | 需注意偏差，宜多专家校验 |

### 3. 敏捷估算

- 故事点衡量**相对规模、复杂度和不确定性**；
- 计划扑克用于团队共识估算，常用斐波那契序列；
- T-shirt估算用于早期粗略分类；
- 速率用于预测本团队未来迭代容量，**不能跨团队比较或用于奖惩**；
- MVP用于最小成本验证关键价值假设。

## 第六记：规划并管理预算和资源

![预算结构与挣值](/donot-eat-fish/img/project-management/pmp-exam/budget-earned-value.png)

### 1. 预算结构

- 活动成本估算汇总为工作包；
- 工作包与控制账户内包含**应急储备**，共同构成成本基准；
- 成本基准加**管理储备**构成项目预算；
- 应急储备用于已识别风险；管理储备用于未知—未知，使用通常需治理批准并更新成本基准。

### 2. 挣值公式

| 指标 | 公式 | 判断 |
|---|---|---|
| 成本偏差 CV | EV - AC | >0节约，<0超支 |
| 进度偏差 SV | EV - PV | >0提前，<0落后 |
| 成本绩效指数 CPI | EV / AC | >1好，<1差 |
| 进度绩效指数 SPI | EV / PV | >1快，<1慢 |

**注意：**SPI不能替代关键路径分析。项目整体SPI良好，也可能存在关键路径活动延误。

### 3. 资源问题处理

- 内部资源冲突：先与职能经理/其他项目经理协商；
- 多项目优先级冲突：由PMO、项目集治理或发起人层面重新排序；
- 特定技能内部无法获得：依据资源管理计划和自制或外购决策，启动采购临时专家；
- 不应直接永久招聘、无限延期或要求发起人“强压”资源，除非正常谈判失败且问题超权限。

## 第七记：规划和管理质量

![质量管理工具图谱](/donot-eat-fish/img/project-management/pmp-exam/quality-management-tool-map.png)

### 1. 三个过程的边界

| 过程 | 目的 | 典型活动 |
|---|---|---|
| 规划质量 | 确定标准和如何达到 | 质量指标、角色、质量成本、验收标准 |
| 管理质量 | 将计划转化为可执行过程并改进 | 审计、根因分析、过程改进、最佳实践 |
| 控制质量 | 检查具体成果是否合格 | 检查、测试、统计抽样、缺陷记录与修复 |

### 2. 质量工具快速判断

- 因果图：找根本原因；
- 控制图：判断过程是否稳定，关注控制限和非随机模式；
- 帕累托图：按频率排序，优先解决少数关键原因；
- 直方图：显示数据分布；
- 散点图：分析两个变量的关系；
- 流程图：理解过程、冗余和决策点；
- 核查表：收集缺陷数据；核对单：确认步骤完整；
- 统计抽样：无法全检的大批量产品；
- 质量审计：过程合规、最佳实践、已批准变更是否实施，不负责直接修复缺陷。

### 3. 质量成本

- 预防成本：培训、流程设计；
- 评估成本：检查、测试；
- 内部失败成本：交付前返工；
- 外部失败成本：交付后赔偿、维修、声誉损失。

考试通常倾向“预防胜于检查”，但应通过成本效益分析选择经济合理的质量水平。

## 第九记：评估和管理风险

![风险管理全链路](/donot-eat-fish/img/project-management/pmp-exam/risk-management-flow.png)

### 1. 风险与问题

- 风险：尚未发生，具有不确定性；
- 问题：已经发生，具有确定性；
- 已识别风险发生后，应执行预先应对并更新问题日志；
- 未识别事件发生后，使用权变措施，必要时申请管理储备和变更。

### 2. 威胁应对

| 策略 | 含义 | 示例 |
|---|---|---|
| 上报 | 超出项目边界或PM权限 | 宏观政策、组织级重大风险 |
| 规避 | 消除威胁根源或改变计划 | 删除高风险工作包、改变技术路线 |
| 减轻 | 降低概率或影响 | 增加测试、采用可靠供应商、冗余设计 |
| 转移 | 将财务/执行责任转给第三方 | 保险、外包、担保 |
| 接受 | 不主动改变，准备储备或监控 | 设应急储备、触发条件 |

机会对应：开拓、提高、分享、接受、上报。

### 3. 高频工具

- 概率影响矩阵：定性排序；
- 风险数据质量评估：验证信息可信度；
- 敏感性分析/龙卷风图：识别影响最大的变量；
- 决策树与EMV：比较不同方案的期望货币价值；
- 风险审查会议：识别新风险、重新评估现有风险、关闭过时风险；
- 风险审计：评价风险过程有效性和合规性。

## 第十记：规划和管理采购

![采购合同选择树](/donot-eat-fish/img/project-management/pmp-exam/procurement-contract-decision-tree.png)

### 1. 采购文件

| 文件 | 作用 |
|---|---|
| 采购管理计划 | 采购流程、角色、协调、合同类型选择原则 |
| 采购工作说明书SOW | 描述采购范围、需求和验收标准 |
| RFI | 获取市场和供应商能力信息 |
| RFP | 邀请供应商提供综合技术/商业方案 |
| RFQ | 范围明确时询价 |
| 供方选择标准 | 技术、价格、经验、资格、风险等加权标准 |
| 卖方建议书 | 供应商对招标文件的正式响应 |
| 独立成本估算 | 验证报价合理性 |

### 2. 合同风险分配

- 固定总价：范围明确，卖方承担较多成本风险；
- 总价加经济价格调整：长期项目、通胀或汇率波动；
- 成本补偿：范围/成本高度不确定，买方承担较多风险，应加强审计和激励；
- 工料合同：类似单价合同，适合短期外部专家或工作量不确定但不复杂的服务。

### 3. 采购工具

- 自制或外购分析：判断内部完成、采购、租赁等；
- 市场调研：不了解供应市场；
- 投标人会议：统一答复潜在卖方问题，保证公平；
- 建议书评价：依据供方选择标准打分；
- 谈判：选定卖方后形成协议；
- 绩效审查：评价卖方范围、进度、成本、质量和合同遵守情况；
- 检查：验证具体成果质量；
- 审计：验证采购过程合规性；
- 索赔：先谈判，再ADR，最后诉讼。

## 第十二记：管理项目工件

![可交付成果与配置管理](/donot-eat-fish/img/project-management/pmp-exam/deliverables-configuration-management.png)

### 1. 可交付成果状态

1. 指导与管理项目工作产生“可交付成果”；
2. 控制质量产生“核实的可交付成果”；
3. 确认范围产生“验收的可交付成果”；
4. 结束项目或阶段完成正式移交。

### 2. 配置管理

- 配置项：可交付成果、受控文档、产品组件等；
- 配置管理系统：存储版本、基线、访问权限和变更历史；
- 版本控制：分支、合并、回滚、新旧版本；
- 配置审计：核对基线一致性、物理状态和合规性；
- 变更控制系统：提交、分析、批准和跟踪变更；
- 敏捷中的文档原则：**足以支持价值、协作、合规、维护和知识传递即可**，不是零文档。

## 第十三记：执行需要紧急交付商业价值的项目

### 1. 产品待办列表相关概念

| 概念 | 作用 |
|---|---|
| 产品待办列表 | 需求池，按价值、风险、依赖和学习价值排序 |
| 用户故事 | 从用户视角描述需求与价值 |
| 史诗故事 | 大型需求，需要拆分到多个迭代 |
| DoR | 进入开发前的就绪条件 |
| DoD | 可交付成果完成、质量和验收的共同标准 |
| MVP | 最小可行产品，用于验证市场或价值假设 |
| 影响地图 | 从目标—参与者—行为—功能连接战略与需求 |

### 2. 优先级工具

- MoSCoW：Must/Should/Could/Won’t；
- Kano：基本、性能、愉悦需求；
- 100点法：有限预算投票；
- 相对排序：直接比较价值、风险和成本；
- 技术债务、合规、安全和风险降低工作也必须纳入优先级，而非只看新功能。

## 第十六记：管理项目变更

![一体化控制框架](/donot-eat-fish/img/project-management/pmp-exam/integrated-control-framework.png)

预测型变更流程：

1. 识别并记录变更；
2. 查阅变更管理计划；
3. 团队与项目经理分析范围、进度、成本、质量、风险、资源和合同影响；
4. 制定建议方案；
5. 由CCB或授权人审批；
6. 批准后更新基准、计划和项目文件；
7. 实施、通知、验证；
8. 拒绝则记录决定并通知申请人。

敏捷中变化通常进入产品待办列表，由产品负责人按价值重排；但预算上限、合同、合规或治理基准变化仍可能需要正式审批。

## 第十七记：规划和管理收尾或过渡

![问题变更收尾边界](/donot-eat-fish/img/project-management/pmp-exam/issue-change-closure-boundaries.png)

### 预测型收尾顺序

1. 获得最终验收，确认范围完成；
2. 验证运营/接收团队准备就绪并移交所有权；
3. 完成采购、财务、法律和行政收尾；
4. 发布最终报告并完成绩效评价；
5. 整理经验教训和项目综合评估；
6. 归档；
7. 获取干系人反馈与满意度；
8. 认可团队并释放资源。

### 敏捷会议区别

- 迭代评审：看“做出了什么、价值如何、下一步优先级”；
- 迭代回顾：看“团队如何工作、过程如何改进”；
- 发布/项目收尾：确认产品/项目目标、运营交接、合同财务、知识和资源收尾。

## 过程域综合记忆

> **方法决定计划方式，范围决定做什么，进度和财务决定何时与花多少，质量决定做到什么标准，风险和采购处理不确定与外部依赖，工件保持信息可信，变更保护决策完整，收尾确保价值真正转入运营。**

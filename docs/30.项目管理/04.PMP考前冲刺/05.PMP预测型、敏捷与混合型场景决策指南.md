# PMP预测型、敏捷与混合型场景决策指南

PMP不要求考生“站队”某一种方法，而要求根据不确定性、风险、价值节奏、团队能力、客户参与、合规和治理要求选择并裁剪方法。

![生命周期选择决策树](/donot-eat-fish/img/project-management/pmp-exam/lifecycle-selection-decision-tree.png)

## 一、先识别题目属于哪种环境

### 预测型信号

- 已批准基准、WBS、详细进度；
- 变更控制委员会CCB；
- 正式验收和阶段门；
- 固定总价合同、明确SOW；
- 建筑、硬件、监管、依赖强且返工成本高。

### 敏捷型信号

- 产品负责人、Scrum Master、自组织团队；
- 产品待办列表、用户故事、故事点；
- 迭代规划、每日站会、评审、回顾；
- 频繁反馈、需求变化、增量交付；
- WIP限制、看板、燃尽/燃起图。

### 混合型信号

- 软件敏捷、硬件或供应商预测；
- 公司要求传统治理报告，但团队采用Scrum；
- 设计阶段需要频繁确认，施工阶段严格按规范；
- 预算/里程碑固定，范围细节在迭代中演化。

## 二、生命周期选择矩阵

| 维度 | 预测型 | 敏捷型 | 混合型 |
|---|---|---|---|
| 需求稳定性 | 高 | 低 | 不同组件不同 |
| 技术不确定性 | 低 | 中高 | 局部高 |
| 客户参与 | 里程碑/验收 | 持续参与 | 关键阶段持续 |
| 交付节奏 | 一次或阶段 | 高频增量 | 按组件/阶段 |
| 变更成本 | 高，需正式控制 | 通过重排吸收 | 基准+待办列表双机制 |
| 合同 | 固定总价常见 | 灵活范围、增量采购 | 多合同组合 |
| 团队 | 职能分工可较强 | 跨职能、自组织 | 治理与团队方式并存 |

## 三、敏捷计划体系

敏捷不是无计划，而是分层计划：

1. 产品愿景：为什么做、为谁创造什么价值；
2. 产品路线图：主要结果和方向；
3. 发布计划：多个迭代和MVP；
4. 产品待办列表：按价值排序的动态需求池；
5. 迭代计划：团队根据容量选择工作并承诺；
6. 每日站会：短周期调整；
7. 评审与回顾：产品反馈和过程改进。

![敏捷会议与工件](/donot-eat-fish/img/project-management/pmp-exam/agile-events-artifacts.png)

## 四、敏捷会议高频辨析

| 会议 | 参加者/主导 | 回答的问题 | 不做什么 |
|---|---|---|---|
| 待办列表梳理 | PO+团队 | 故事是否清晰、可估算、如何拆分和排序 | 不做最终迭代承诺 |
| 迭代规划 | PO讲价值，团队承诺 | 本迭代做什么、如何做 | PM不应强制分配全部任务 |
| 每日站会 | 团队 | 进展、计划、障碍 | 不做长时间问题解决会 |
| 迭代评审 | 团队+PO+干系人 | 增量是否有价值、下一步调整什么 | 不主要讨论团队过程 |
| 迭代回顾 | 团队 | 工作方式如何改进 | 不替代产品验收 |
| 发布规划 | PO、团队、关键干系人 | MVP、路线图、多迭代节奏 | 不承诺不可变的长期细节 |

### 典型题

- 新故事模糊、缺验收标准：在**待办列表梳理会**澄清；
- 团队发现强制参数缺失：立即在**每日站会**作为障碍提出；
- 产品负责人不满意已完成功能：在评审中获取反馈，更新验收标准/待办列表并重新排序；
- 团队工作方式需要改进：在回顾会形成行动项。

## 五、敏捷工件和指标

### 1. DoR与DoD

- DoR：故事进入迭代前是否足够清晰、可估算、依赖可控；
- DoD：成果是否满足共同质量、测试、文档、合规和验收标准。

DoD是团队共享的完成标准，不等同于单个故事的全部业务验收标准，但可以包含共同质量门槛。

### 2. 燃尽图与燃起图

- 燃尽图显示剩余工作，适合看是否按趋势完成；
- 燃起图显示已完成量和总范围，能更好显示范围变化；
- 速率是团队历史交付能力，不应用于跨团队比较和奖惩；
- 累计流量图用于观察WIP、队列和瓶颈；
- 流动指标应与质量和业务结果一起看，不能只追求“做得更多”。

## 六、产品待办列表优先级

| 方法 | 用途 |
|---|---|
| MoSCoW | 区分必须、应该、可以和暂不做 |
| Kano | 分析基本、性能和愉悦需求 |
| 100点法 | 让干系人在有限点数下表达真实偏好 |
| 相对排序 | 两两比较价值、风险、成本、依赖 |
| 风险价值排序 | 优先高风险、合规、安全和学习项 |

产品负责人负责排序，团队提供技术、成本、风险和依赖信息。项目经理/Scrum Master不替PO决定业务价值。

## 七、服务型领导与自组织

敏捷领导者：

- 保护团队免受干扰；
- 清除障碍；
- 促进透明和反馈；
- 教练干系人正确参与；
- 建立共同规则和心理安全；
- 让团队决定如何交付；
- 不通过微观管理提高速度。

当干系人频繁电话邮件询问状态时，应提供信息发射源和正确沟通接口，并指导其敏捷参与方式，而不是让开发团队不断中断。

## 八、预测型变更与敏捷变化的区别

| 情况 | 预测型 | 敏捷型 |
|---|---|---|
| 新需求 | 记录→影响分析→审批→更新基准 | 进入待办列表→PO排序→未来迭代 |
| 已承诺迭代内新需求 | 通常不直接插入 | 除非团队与PO重新协商迭代目标 |
| 合规/安全变化 | 正式分析和变更 | 进入高优先级待办，必要时治理审批 |
| 预算/合同变化 | 正式变更 | 仍需治理与合同变更，不能只靠排序 |
| 缺陷 | 缺陷修复，影响基准时变更 | 按DoD修复，未完成不能算完成 |

## 九、混合型治理模型

![预测型与适应型主流程](/donot-eat-fish/img/project-management/pmp-exam/predictive-adaptive-main-flow.png)

混合项目常见的正确设计：

- 组织层：商业论证、章程、预算上限、里程碑、治理报告；
- 产品层：路线图、发布计划、产品待办列表；
- 团队层：迭代计划、站会、评审、回顾；
- 供应商层：明确组件使用固定总价，探索性专家使用T&M/成本补偿；
- 变更层：产品细节由待办列表管理，基准/合同/法规变化走正式变更。

## 十、敏捷情境题常见陷阱

| 错项 | 错因 |
|---|---|
| 项目经理给每个人分配任务 | 破坏自组织 |
| 让团队盲目对截止日期负责 | 忽略容量、依赖和持续计划 |
| 比较不同团队速率并奖励 | 速率不可跨团队比较，诱发估算膨胀 |
| 把文档全部删除 | 敏捷强调足够文档，不是零文档 |
| 客户不参与时团队自行猜测 | 缺少价值反馈，应促进客户/PO参与 |
| 障碍等到回顾会再说 | 障碍应立即透明化和处理 |
| 为赶进度推迟合规检查 | 合规和质量应内建 |
| 新需求直接塞入当前迭代 | 破坏迭代目标和团队承诺 |

## 十一、预测/敏捷/混合统一判断口诀

> **明确稳定用预测，模糊变化用敏捷；分批可用是增量，反复优化是迭代；约束与探索并存，用混合按组件裁剪。**

> **预测保护基准完整，敏捷保护价值和反馈；两者都需要治理、质量、风险、透明和责任。**
